# B 站三种内置登录设计

日期：2026-10-02
状态：待用户书面评审；尚未编写实施计划或产品代码。
适用项目：LAPTOP-MIYAKO0721 上的 game-manage，正式服务为 http://127.0.0.1:8010。

## 1. 已确认的目标与边界

用户已接受非公开接口、依赖停维护和当前 HTTP 412 的限制，同意提供账号密码、手机号验证码、扫码三种内置登录，默认扫码，保留 Cookie 导入备用。

本功能用于各游戏共用的 B 站资讯采集账号，不改变鸣潮、异环、终末地各自的游戏社区登录，也不增加 B 服游戏角色登录。密码和短信验证码不落盘；登录成功并验证候选凭据后，才替换现有 DPAPI 凭据。失败、取消或超时保留原账号和已采集数据。验证码由用户手动完成，不绕过 CAPTCHA、HTTP 412 或其他访问限制。真实账号的登录验收由用户自行操作。

本次不加入安全中心验证接口、自动续期、代理切换、浏览器自动化、多账号管理、账号注销或其他业务功能。书面方案获批后再编写实施计划，由父对话协调执行方式和之后的部署；本轮只产出设计文件。

## 2. 调查依据与可用性结论

调查基线为 main / d3f7b9354d9d5f38c295604268e5632fa734b5e1，调查结束时工作树干净，本机 /api/health 和 /openapi.json 返回 200。

- frontend/src/components/BilibiliSourcePanel.vue 的 saveLogin 和表单目前只收集 SESSDATA、可选 bili_jct、buvid3。
- sources/bilibili_routes.py 只有 POST /api/auth/bilibili-source/credentials 保存入口。BilibiliService.login_state 只检查 SESSDATA 是否存在，没有登录有效性验证。
- 凭据路径为数据库路径改后缀得到的 .bilibili.credentials.json；CredentialStore 已实现当前 Windows 用户 DPAPI 和原子文件替换。
- pyproject.toml 要求 bilibili-api-python >=17.4.1,<18，uv.lock 和本机均为 17.4.2。安装代码含 login_with_password、send_sms、login_with_sms 和 QrCodeLogin；密码、短信需要人工验证，也可能返回 LoginCheck。

## 3. 选定结构与修改范围

选定独立、可替换的 B 站登录适配层。由有限的 HTTPX 调用处理登录协议，复用现有加密存储；现有 SDK 继续负责资讯读取。这样可以兼容 QR 新旧响应，不依赖归档 SDK 的原扫码解析，也不修改 site-packages 或全局 monkey-patch。OAuth 不直接满足当前采集凭据需求；浏览器辅助接入会引入新的运行依赖，本轮不采用。

组件职责：

- 新增 frontend/src/components/BilibiliLoginPanel.vue：四个入口（扫码、账号密码、手机号验证码、Cookie 导入），人工验证、倒计时、错误和保存重试。BilibiliSourcePanel 负责展示入口和接收成功事件，保留采集与审计界面。
- 新增 frontend/src/bilibili-auth-api.js：统一请求、超时、取消和安全错误读取。
- 新增 src/game_assistant/auth/bilibili_provider.py：固定上游地址、验证码初始化、密码加密、短信交换、扫码解析和候选凭据验证；不负责持久化。
- 新增 src/game_assistant/auth/bilibili_service.py：内存会话、限流、并发控制、结果版本检查和唯一凭据提交出口。
- 扩展 sources/bilibili_routes.py 和 sources/bilibili_service.py；api.py 组装服务并在应用关闭时清理会话。保留现有 CredentialStore 加密实现。
- 补充对应测试、docs/community-login.md 和 docs/bilibili-source.md。若二维码生成所用 qrcode 当前仅为传递依赖，将其显式声明并更新锁文件；不以整体升级 SDK 为前提。

B 站登录服务与采集服务共享同一个 CredentialStore。登录服务验证后调用采集服务的内部提交出口，其他 HTTP 入口不得直接保存未经验证的凭据。没有配置 B 站来源时沿用现有面板显示规则；登录接口返回 SOURCE_UNCONFIGURED，不为本功能增加来源配置功能。

## 4. 本地 API 契约

新接口前缀为 /api/auth/bilibili-source/login。所有新路径均多一层 login，避免被已先注册的 /api/auth/{game}/sessions、/sms、/login 截获。

所有写请求继续要求 X-Game-Assistant: 1、受信任 Host/Origin、JSON 请求体上限 16 KiB。读取接口只返回本地缓存状态；响应使用 no-store / no-cache / no-referrer。会话 ID 必须为完整匹配的随机值，不参与文件路径或上游 URL 拼接。

| 方法与路径（相对此前缀） | 输入 | 输出或行为 |
| --- | --- | --- |
| GET /status | 无 | 现有账号的 configured、state、uid、nickname、validated_at、安全提示；无凭据 |
| POST /sessions | mode: qr/password/sms/cookie | 创建会话，返回 session_id、mode、state、expires_in；QR 模式同时返回本地生成的二维码图像及其剩余展示时间 |
| GET /sessions/{sid} | 无 | 缓存状态、剩余时间、是否可重试保存和安全错误；不访问上游 |
| DELETE /sessions/{sid} | 无 | 取消该会话；已提交完成的账号不回滚 |
| POST /sessions/{sid}/captcha | 无 | 仅 password/sms；取得新人工挑战，返回类型及展示所需 gt、challenge，登录 token 留在服务端 |
| POST /sessions/{sid}/password | username、password、captcha: validate/seccode | 密码交换、验证和提交；账号输入支持上游已确认的手机号/邮箱形式 |
| POST /sessions/{sid}/sms/send | mobile、captcha: validate/seccode | 大陆手机号发送短信，返回 retry_after；手机号与短信票据绑定此会话 |
| POST /sessions/{sid}/sms/submit | code | 仅使用该会话已绑定手机号和服务端短信票据交换、验证和提交 |
| POST /sessions/{sid}/qr/poll | 无 | 获取一次扫码状态；完成时立即捕获候选凭据、验证和提交 |
| POST /sessions/{sid}/cookie | sessdata、可选 bili_jct/buvid3 | 导入、验证和提交 |
| POST /sessions/{sid}/commit | 无 | 只提交内存中已经验证且仍有效的候选凭据，不重新消费二维码或重复提交密码/短信码 |

正常响应包含 state；成功响应包含 ok: true 和脱敏 account。已有验证候选时，采集运行中返回 409 / pending_save，存储失败返回 500 / pending_save；前端读取安全状态字段显示“重试保存”，原账号保持不变。错误结构为 {detail, error_code, state?, retry_after?}，不回传上游响应。状态码约定：422 本地输入错误，410 会话过期/取消，409 模式、在途操作或账号版本冲突，429 本地/上游限流，502 上游不可用，500 本地存储失败。上游 HTTP 412 映射为 502 / UPSTREAM_RESTRICTED，界面停止轮询并提示稍后由用户重试。

原 POST /api/auth/bilibili-source/credentials 保留兼容，内部转交同一导入、验证及提交流程；保留成功响应 ok/configured，不再提供跳过验证的保存路径。新增错误字段为可选字段，不改变游戏社区登录路由。

## 5. 短期会话、取消与并发

每个会话包含随机 32 字节生成的 sid、mode、单调时钟期限、generation、创建时账号 revision、尝试次数，以及该模式的临时上下文。最多一个活动 B 站会话，供所有资讯面板共享；新建会话使旧会话失效，不退出已保存账号。成功/取消后敏感上下文立即清理，脱敏终态最多保留 60 秒供请求超时后的状态确认，记录总数限制为 16。

- 会话最多 10 分钟；QR 本地展示期限最多 180 秒，收到上游过期状态立即失效，不声称这是上游保证的有效期。人工挑战本地最多使用 120 秒，且一次登录/发送尝试后即消耗。
- 验证挑战绑定 sid、mode、generation；token 和 challenge 来源由后端记录，不接受客户端替换。密码首次提交绑定账号，短信首次发送绑定手机号；切换账号、手机号或登录方式必须新建会话。
- 每个会话最多一个上游操作在途。网络请求在锁外执行；返回后重新检查 sid、generation、期限、账号 revision 和取消状态，全部匹配才接收结果。密码或短信码提交最多 5 次，达到上限使会话失效。
- 新建会话上限为每分钟 10 次。短信按区号和手机号摘要限制每 60 秒一次，并限制全局每 10 分钟最多 5 次；先预留发送次数再访问上游。网络超时也消耗冷却，不自动重发。当前范围沿用应用的中国大陆手机号规则，区号固定 +86。
- QR 前端每 3 秒轮询一次，后端同一会话也限制为 3 秒一次；更早的重复请求返回缓存。使用一次性定时器，关闭面板、切换方式、取消、过期、完成或被限制时停止。
- 单个上游请求超时 10 秒，一次交换加验证总时限 60 秒；前端等待上限 75 秒。超时后不自动重放密码、发送短信或成功扫码请求，先查询会话状态。取消和关闭调用 DELETE，AbortController 中断前端等待；后端在提交前检查取消/断连状态。
- 凭据提交与采集启动协调：检查是否有运行中的采集，检查 revision，再执行同步原子保存；关键段不跨网络 await，避免新采集与替换交错。采集运行时保留已验证候选在内存，用户可重试保存。
- pending_save 最多保留 120 秒且不超过会话期限。超出后清理候选，要求重新登录。重试提交前再次验证候选，避免保存等待期间已失效的登录态；与首次提交相同的版本/取消检查必须执行。
- 提交成功才增加 revision。迟到请求、旧页面的取消请求和旧会话的保存重试不能覆盖较新账号。若提交已完成才收到取消，返回 complete；用户可以刷新状态确认，不能宣称已撤销成功保存。
- 进程重启或应用关闭清理所有短期会话；已有加密账号继续保留，不从日志或临时文件恢复待登录过程。

## 6. 三种登录与 Cookie 导入

### 扫码（默认）

后端调用当前 WEB QR 生成接口，本地内存生成二维码；不写共享 qrcode.png，也不把登录 URL 发给第三方二维码服务。前端仅展示本地返回的图像，不额外暴露原始轮询密钥、票据或 refresh_token；二维码本身仅限当前本地会话展示，不缓存。

轮询明确识别待扫码 86101、待确认 86090、已过期 86038 和成功 0；未知码不是成功。成功时在同一次响应处理中捕获凭据，不能事后再次轮询补取已消费的票据。

- 旧格式：从成功 URL 的查询参数解析 Cookie，检查必要字段完整。
- 新格式：识别明确的 crossDomain 票据地址，按固定允许列表访问并收集响应及允许重定向中的 Set-Cookie。
- 只允许 HTTPS、默认端口、无 userinfo；票据和中间跳转仅接受 passport.bilibili.com / passport.biligame.com 的 /x/passport-login/web/crossDomain 路径。最终跳转到 www.bilibili.com 根页面可终止，不继续访问任意页面；其他路径需有明确验证样本并重新适配后才开放。最多 3 次跳转，每一步均检查地址；禁止跟随其他域名、IP 地址或自定义端口。
- 只从这些响应的允许 Cookie 名称提取值；拒绝相互冲突的重复凭据、空凭据、畸形 URL、过大的值和结构不匹配的响应。协议不符时报告不可用，保留原账号。
- 两种格式最后都必须通过同一凭据验证；显示“扫码成功”不等于保存成功。

新格式依据公开问题报告设计，真实响应格式仍需用户验收确认；不直接引入 PR 27 未审补丁。实现时只接受已明确建模的格式，不尝试猜测新接口或跟随任意返回地址。

### 账号密码

用户输入账号和密码并完成人工验证。后端取得动态公钥与盐后立即 RSA PKCS#1 v1.5 加密并提交；不跨请求缓存公钥，也不保存明文密码或 RSA 密文。密码原样处理，不 trim，长度和加密载荷超限给出本地安全错误。密码只在请求局部变量中存在，不能进入服务会话、日志、异常或状态响应；清理局部引用不等于承诺 Python 内存的物理擦除。

成功后解析 Cookie 并验证；返回额外安全验证状态、LoginCheck 类结果或未知状态时，不视为成功。界面提供固定官方登录页链接，让用户自行完成验证后重新开始内置登录或 Cookie 导入，不调用安全中心接口。

### 手机号验证码

先完成本次会话人工验证，用户点击后才发送短信。服务端保存当前手机号与发送返回的 captcha_key，提交短信码时不接收客户端替换手机号或票据。超时、限流或失败不自动再发短信；修改手机号要求新会话。成功后验证并提交，额外安全验证处理同密码方式。短信码仅存在于提交请求的局部变量。

### 人工验证码与 Cookie 兼容

B 站验证码使用独立的协议适配和受控 HTTPS 官方 Geetest 客户端脚本，加载失败则禁用密码/短信提交；不使用 SDK 自带验证码服务器或旧的内嵌脚本。初始化只返回展示所需的公开挑战参数；前端仅提交人类完成后的 validate/seccode，后端补齐记录的 challenge/token。前后端的旧回调均进行 generation 检查，禁止模拟、代做或重放挑战。

Cookie 导入在“备用方式”中保留。新三种登录要求完整 SESSDATA、bili_jct、DedeUserID；兼容导入仍允许只填 SESSDATA，由验证接口确认登录身份后补充 dedeuserid，可选字段仅用于现有只读采集。解码只进行一次：URL 查询值由解析器解码一次，原始 Cookie/导入值由规范化器解码一次，内部提交不再无条件 unquote。验证与保存使用同一规范化结果。

## 7. 验证、存储与日志

验证使用固定的 https://api.bilibili.com/x/web-interface/nav，仅携带候选 Cookie，检查响应 code == 0、data.isLogin == true 和有效正整数 UID；已有 DedeUserID 必须与返回 UID 一致。错误、HTTP 412/429、超时或匿名响应均不得保存；新候选验证失败不能据此把旧账号标为失效。验证接口仍是非公开网页协议，不标作官方开放 API。

仅保存 sessdata、bili_jct、buvid3、buvid4、dedeuserid、ac_time_value 白名单字段，仍存入根对象 bilibili。显示用 UID、昵称和验证时间可存入独立 bilibili_meta 对象，不传给 SDK Credential 构造器。现有只含 bilibili 的文件可直接读取，无强制迁移。配置存在与本次运行已验证分开显示，旧账号不因文件存在就显示“已验证”。

复用 DPAPI 和原子替换；保存失败保留原文件与内存账号。成功后只重置相关来源的 next_retry，用户继续按现有入口触发采集；不清空公共历史、其他平台凭据或私人快照。重试时间重置失败不把已成功保存说成登录失败，返回“账号已保存，采集刷新可重试”。本轮不修改 config.toml、凭据加密实现或登录失效后的自动续期策略。

凭据文件损坏/不能解密时停止写入，显示固定存储错误，不默默覆盖旧文件或回退到其他凭据。候选验证不会使用旧账号 Cookie；上游请求客户端按会话隔离，TLS 校验开启，不继承代理、不随机伪造设备指纹。若正常协议返回设备标识，仅使用该会话合法取得的值。

日志只记录固定事件名、模式、异常类型、允许的 HTTP/业务错误码和耗时。不记录 sid、账号、手机号、密码、短信码、验证证明、Cookie、token、QR URL、跨域票据、请求/响应正文或原始异常字符串；HTTPX 调试日志不启用。Pydantic 校验错误必须用固定文案替换，不能回显输入。前端成功、关闭或切换方式时清空输入与候选状态，不写 localStorage/sessionStorage，也不把敏感值放入 URL。

## 8. 测试与验收

已执行的调查基线：相关后端 151 项通过（2 个依赖弃用警告），前端 auth-api、LoginPanel、BilibiliSourcePanel 共 21 项通过。测试使用模拟账号、隔离临时目录；不证明真实登录可用。写设计文档不需要重跑产品测试。

新增测试覆盖：

- Provider：三种流程正确表单、RSA 实际解密断言、人工证明缺失/错会话、短信票据绑定、额外验证和未知状态拒绝。
- QR：所有轮询状态，旧查询参数与新 Set-Cookie 样本，成功仅消费一次，恶意地址/跳转拒绝，缺失或冲突 Cookie，双重解码防护，nav 匿名/UID 不符拒绝。
- Service：模拟时钟验证期限、短信冷却、尝试上限、单个在途请求；取消/切换/重启/旧结果失效；采集运行时 pending_save、过期清理、提交前再验证、原子保存失败保留旧账号。
- 路由与安全：新路径不会命中通用游戏路由，旧导入入口不能绕过验证，Host/Origin/写请求头/体积限制，422/异常不回显敏感值，所有响应禁止缓存。
- Vue：默认扫码、四种入口切换、人工验证加载失败、发送按钮冷却、单一轮询、取消/卸载清理、迟到响应忽略、保存重试和账号显示更新。接口和验证码组件均模拟，不触发真实短信。
- 回归：其他平台登录、B 站资讯与历史保留、旧 DPAPI 文件兼容、不向 SDK 注入 metadata；对日志/API/前端存储设置假敏感哨兵值并断言没有泄漏。

实施后先运行上述相关测试，再按仓库现有 CI 执行后端测试、前端测试和构建；测试数据必须与正式 config/data 隔离。三种方式各自的真实成功验收由用户手动完成：检查已验证账号、保存后重启可读取，以及原采集功能正常。账号密码和短信若被要求额外验证，必须显示准确限制；不能用扫码成功替代另外两种验收。

若本机继续返回 HTTP 412，保留功能与明确错误提示，但该方式标记为“未完成真实验收”；不以模拟测试通过声称三种方式均可实际使用，不为验收绕过访问限制。
